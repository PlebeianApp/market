A reading guide to one module

The validation module, in plain language

One module that checks the content of a record against rules a host hands in, at the one place records are accepted. Hand it no rules and it does nothing at all — it refuses nothing. This page explains the job, the two rule kinds, the three outcomes, the six bounds, how the module was attacked, what was measured, and the parts that are not finished.

CHAPTER 01

What the module is, and why it exists

A module that checks the content of a record — its shape, its tags, its values, and the things it points at — against rules the host wrote, at the single place records are let in. On its own it decides nothing.

The job, in one sentence. Validate an event's content against presets a host supplies, at an accept boundary, and — with no presets supplied — do nothing at all: it is a pass-through that refuses nothing.

Three words recur on this page and are worth fixing now. An event is one published item: a product listing, a review, an order message. A preset is the host's own declaration of the shape it demands for one kind of event, and the checks to run against it — the module ships none of its own. A check is one rule inside a preset, and there are exactly two kinds of them, both data (chapter 3).

Where it came from, said exactly

The spec was written at its final state — the module as it should be, not as anything is today; a Rust, Angular or Flutter version would satisfy the same spec. The first implementation is TypeScript, in validation/ts/: the contract's three exports and eight types, built on 2026-09-30 as the run's fourth increment, then repaired twice the same day. The spec's own opening sentence — “this is a spec and only a spec; no ts/ exists” — is what the document said before the increment; its own amendment records the change rather than letting the sentence go stale, and no declaring line was edited to say so.

The spec

Written at its final state, with sixteen declaring lines. Its D-O24 and D-O25 amendments add the placement (one gate) and the vocabulary (two rule kinds, three outcomes, six bounds) without editing a single declaring line.

The first implementation

TypeScript, ten source files plus a host-side harness and one test file. Its rules are data, its engine is kind-blind, and its one dependency is nostr-tools — applesauce-core and rxjs appear in neither dependency list.

Why build it before anything composes it

The module is on no critical path: nothing in the run imports it, the store ships without it, and the composition's gate is a decision rather than a build. What it buys is that the contract was written and executed before a consumer had a chance to shape it by accident. Chapter 8 keeps that cost visible.

CHAPTER 02

The contract — two operations, one gate

Everything a consumer may call: two operations, three exports and eight types. One operation is the module's own entry; the other is the composition's accept hook, so the module never grows a boundary of its own.

01 validate(event)

The module's own entry, for a host that calls it directly. It answers with an outcome value: accepted, refused (carrying the preset, the check, the cause and — for a format — the requirement), or quarantined. A candidate's verdict is never an exception.

02 accept(event, context)

The composition's hook. Same evaluation, mapped to the two-word answer a gate needs — accept for an accepted candidate, reject for every other outcome. Quarantine therefore inherits the gate's own word: not admitted. The context — the flow, the tier, and the resolve a link needs — reaches the module.

Every refusal has a name, and no verdict is a string

Nothing in this contract fails with a bare string or a silent drop. A refusal carries the preset and the check that fired, in a value a caller reads. A bound that is exceeded is an outcome, not an exception. The only throw is a preset the engine cannot interpret — a comparator outside the closed vocabulary, a chain depth above one hop, or a third rule kind — and it fires at the preset, before any candidate is judged.

CHAPTER 03

The two rule kinds, both data

A preset's checks are exactly two kinds and no third. Both are values a consumer passes in, never an opaque function — because a rule a test cannot read is a rule a test cannot falsify.

A format, in a sentence

“For this kind, here is the shape I demand”: the tags that must be present, how many of each, which values are inside the domain, and how much content is allowed. Every failure reports which of those four requirement kinds it was.

A link, in a sentence

“This event must satisfy something about another event”: name the reference, name how to fetch it, and name the fields to compare — then the comparison to run. The module follows the reference and compares; it does not know why those fields matter.

Exactly two, and why that is a rule rather than a limit

The spec fixes exactly two rule kinds and no third. A third kind would mean the engine taking on semantics, and a rule a test cannot read would be a rule a test cannot falsify. A preset set with no rules is pass-through — the spec's own default, and the reason a host that declares nothing gets exactly today's behaviour. The market's existing NIP-99 format declarations are the first thing this module would activate rather than re-invent; chapter 8 records that they are not activated yet.

CHAPTER 04

The three outcomes, and what a caller reads

Two outcomes cannot express the truth about a reference nobody could answer, so there is a third. Pick a case below and see the value a caller would read — nothing here is hidden behind the motion.

The requirement: the repair that came out of the red team

A format is one rule that may carry several requirements at once. The red team found that when it does, three different failures carried the same value — one (cause, check.id) pair — and were separable only by free text. The repair gave every format refusal a requirement: 'missing-tag', 'cardinality', 'domain' or 'content'. This is a different axis from the four causes, which stay four; a format refusal's cause is still 'differs'. Chapter 6 tells that story in full.

What the caller always gets

An outcome, never a bare string and never a silent drop. A refusal names its preset and its check — and, for a format, the requirement. A quarantine names the check and the reason it could not be answered. The gate reads one word — accept or reject — and every outcome that is not accepted becomes reject.

CHAPTER 05

The six bounds, each with a mechanism

Quarantine needs a ceiling or it is a way to hold everything forever, so the spec declares six bounds. Each is part of the contract rather than tuning, each is overridable per preset, and — this is the load-bearing clause — each has a mechanism.

What “a bound is an outcome” means. A candidate that trips a fan-out ceiling or a chain ceiling below one does not throw and is not refused as if its content were wrong: the link resolves as unresolved, which is the quarantine outcome. A deadline that fires is the same — quarantine. The only throw is a preset the engine cannot interpret.

Bound 5, in its own words

Memory held for unresolved references is capped, and when the cap is reached the oldest entry is evicted — recorded as data loss, never a silent drop — and because it has left the held set, the next evaluation re-resolves it rather than forgetting it. The record of evictions is itself bounded (a count plus the last few names), because a memory bound whose own book grows without bound is not a memory bound.

Bound 6, and the clock it needs

The revisit gate is a comparison against the clock. A clock frozen at a constant makes it false forever — a declared bound with no mechanism in a supported configuration, which the module cannot claim. So the default clock is a real clock; an injected port's now() is preferred, and the host's wall clock is the last resort. That one line is the module's only host read.

CHAPTER 06

How it was attacked, and what the attack found

A test that cannot fail proves nothing, so every case was broken on purpose. Separately, two blind reviewers were asked to falsify the module's claims — and one claim did not survive in the shape the spec describes.

The wave, stated plainly

Two blind reviewers each reproduced all nineteen pinned file digests before attacking, and returned micro-harden: five minor findings and four notes from one, and one counterexample-with-a-control from the other. The counterexample is the one above: format refusals collapsed to a single value when one check carried several requirements. It was reproduced by the verifying party before a line changed — one distinct pair in the spec's shape, three in the convenient shape the suite had hand-built — and then fixed by giving every format refusal a requirement. A second repair, dispatched the same day, found that the default clock was frozen, which made bound 6's revisit gate unsatisfiable; the default became a real clock.

The two claims the wave attacked and could not break

The pass-through floor

Driven on both operations, with no presets and with a preset set that does not cover the candidate. It held on both. “A pass-through case with no presets” is one of the spec's own evidence obligations, and it has a case and a mutation under it.

“A quarantined event is never admitted”

The reviewer drove every path that can reach a quarantine — the fan-out ceiling, a chain ceiling, both deadlines, an undefined answer, no resolver, and a spent revisit count — and demanded the hook answer reject on each. It did, with an accepting control proving the hook is not one that always rejects.

What the repair did, in one line each

  • A format refusal gained a requirement, so the difference lives in the value.
  • A resolver that rejects or throws became quarantine — a reference nobody could answer — instead of an exception escaping the module.
  • An uninterpretable preset fails the same way whatever the candidate's state, at the preset, before any resolution.
  • A specific preset now wins over a wildcard, whatever order the host declared them in.
  • Bound 1 counts resolutions attempted; bound 5's eviction record is itself bounded.
  • A preset asking for chain following is refused loudly rather than silently ignored.

CHAPTER 08

What is not yet true

This chapter is deliberately uncomfortable. Everything below is a limit of the module as it stands, taken from its own freeze note and spec — not a caveat, and not softened.

1 · Nothing imports this module

Not event-access, not the store, not the wire, not the market. Its accept conforms to the composition's hook shape and is exercised against a fake of that shape; wiring it into the gate is a later increment's decision, and so is pointing any real host at it.

2 · It ships no preset of its own, and the market's declarations are not activated

The spec names the market's existing NIP-99 format declarations — productListing.ts, productCollection.ts and productReview.ts — as the first thing this module would activate rather than re-invent: they declare shapes and are parsed nowhere. That activation has not happened. A host that declares no preset gets exactly the pass-through default, which is the module's whole behaviour today.

3 · It is not wired into the composition's gate

This module is written as one implementation of the composition's single gate, applied at two sites — but the placement is a decision, not a build. No query's answer is filtered by this module and no publish is dropped by it. The composition side of that boundary is event-access's obligation, stated there.

4 · A second implementation does not exist, so portability is unproven

The whole reason for writing a spec before a second implementation is that a Rust, Angular or Flutter version should be able to meet it. None of them exists, and nothing here demonstrates that the spec is portable. That claim is a claim.

5 · Two limitations are recorded rather than repaired, and two readings stay open

  • The check named in a bound-1 quarantine is still the first link check while the reference is the over-ceiling resolution — the case asserts only what the code does.
  • deleted and expired are unreachable through accept when no port is injected: the gate has no store to know a deletion from, so a vanished reference arrives as quarantine. That is the module's shape, not a defect.
  • Whether a refusal is a rejection the caller must handle or a report it may ignore is left open for the first real composer.
  • The preset language is settled only in shape — that it is data. Which library an implementation adopts for a predicate is that implementation's named exception.

The honest sentence for all of chapter 8

The module's contract, its two rule kinds, its three outcomes, its six bounds and its isolation are written down and executed — 32 green cases and 32 mutations each reddening its named case. What is missing is not effort: it is a host, a real reference, a consumer and a second language. Until those exist, this is a proven design and unproven software.

CHAPTER 09

Open questions, and the assumptions I had to invent

Two readings the spec leaves open for you, and — separated out, so nothing is buried in the prose — the place-names, translations and guesses this page makes on your behalf.

The readings the spec leaves open

1 · Rejection, or report?

Whether a refusal is a rejection the caller must handle or a report it may ignore. A pass-through default and a typed refusal together lean towards the former, and the first real composer settles it. What is not open: the module never warns and lets an event through — “a validation module that warns is a validation module that does not validate.”

2 · The preset language

Settled only in shape: a preset is data — a record naming the kinds it applies to and the requirement it imposes, selecting among host-supplied typed predicates. Whether that data is JSON-Schema-shaped or a typed structure is the increment's choice when it is ordered.

What I invented, and want you to correct if it is wrong

None of the following is in the spec. Each is a decision made to turn a technical document into something readable, and each is the kind of thing that should be corrected in one line rather than argued about:

  1. Every plain-language gloss is mine. The ones most likely to be wrong: event for a record; preset for the host's declaration of a shape and its checks; check for one rule inside a preset; port for a socket the host fills; resolver for the host's answer to a reference; quarantine for the held-and-not-admitted outcome. The comparison vocabulary and the requirement names are the spec's own nouns.
  2. The grouping of the outcomes into “two axes” — the four causes, and the requirement discriminator — is mine. The spec states both; it does not draw them as axes.
  3. The outcome tree is my drawing. The spec carries the same facts as prose, and the picture adds nothing but a shape.
  4. The six bounds are shown with the research note's suggested defaults. The spec declares six bounds; the numbers beside them (ten, one hop, five seconds, thirty seconds, one mebibyte, three revisits five minutes apart) are the suggested defaults of research/11-event-to-event-link-protocol.md §4, not separately invented here.
  5. Every number on this page is quoted from the module's evidence captures (evidence/01-build-and-tests.txt, 02-invariant-falsification.txt) or from the freeze note's own summary of them, rather than recomputed. The countersignature proposition is a computation, which is exactly why it is given as a table rather than as a number.
  6. I chose the balance of this page: the measured wins are given the numbers they earned, and the gaps are given a whole chapter. If that balance is wrong for you, the balance is what to change — the facts are the artifacts'.
