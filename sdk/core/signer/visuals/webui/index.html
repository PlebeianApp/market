CHAPTER 01

What the module is, and why it exists

A signer is the part of an app that knows which account you are on and produces the signatures that prove it. This module is that part, taken out of the app and specified on its own.

The job, in one sentence. Resolve who the user is, sign records for that identity under an explicit rule about what may be signed, and own the session that makes both true — on any host, with the storage backend, the relay connection, the clock and the cryptographic maths supplied by whoever puts the module together.

Three words recur on this page and they are worth fixing now. A record (the code calls it an event) is one published item: a post, a product listing, an order message. An identity is the user's public address — the thing other people can see. The key is the secret that proves it is them; wherever it lives is what chapter 5 is about.

Where it came from, said exactly

Two things that are easy to blur, and the spec keeps them apart deliberately:

The spec

Written at its final state — the module as it should be, not as anything is today. A Rust, Flutter or Angular version of the same module would satisfy the same spec. This is why the document names behaviour rather than code.

The first implementation

TypeScript, in signer/ts/. It began as a credited harvest of the market's own tested signer code at commit 4bc7f8c0, then had the browser-, framework- and app-specific parts cut out. So it is not a design drawn on a blank page, and it is not an extraction from the app either.

Why build it before anything needs it

The project's direction was to write the core modules at their final state rather than waiting for a second consumer. The consumers named in the spec are honest about their status: the marketplace app is the surface being replaced (it still holds its own signer code, and this build did not touch it), a command-line tool is named but not built against this module, and the phone, desktop and command-line hosts the maintainer named do not exist at all.

Why bother, then? Because today the signer is not a thing — it is a behaviour spread through an app. The proposal for this build measured the signer's type reaching into 34 files through 102 hand-passed parameters, with the wallet's start-up, the relay list and some user-facing wording running inside the same lifecycle. Pulling the signer out and giving it a written contract is what stops each new host from inventing its own version of the same decisions.

What that costs, in the spec's own terms

Nothing yet proves this contract is usable by a real composer, and the first consumer will find the places where it is not. What it buys is that the contract was written and executed before any consumer had a chance to shape it by accident. Chapter 8 keeps that cost visible.

One naming note, recorded in the spec rather than corrected: the project's older core document calls this area “authentication”. The maintainer's word, and this module's name, is the signer — because signing records is the job, and authentication is one consequence of it.

CHAPTER 02

The contract — thirteen operations, in plain language

Everything a consumer is allowed to ask for. Thirteen things a session can do, one entry point that has no session at all, and typed refusals instead of silence.

Identity, and signing

01 getPublicKey

“Who am I?” Answers with the user's public address, and it is the only identity read in the module. Everything else — the app, a screen, a command-line tool — asks through here rather than keeping its own copy of who the user is.

02 signEvent

“Sign this prepared record, as me.” Two things must both hold or the answer is refused: the signature must verify, and the record must carry the same address getPublicKey just gave. A perfectly valid signature from the wrong key fails closed.

Encryption — optional on purpose

03 capabilities

“What encryption can you actually do?” Answers with what is genuinely available right now, after the composer's own permission list has been applied. If nothing is permitted, the answer is nothing.

10 encrypt

Encrypt a message to one other person, under a named scheme — and only when that scheme is really present. If it is absent, this refuses rather than invent a key the user never handed over.

11 decrypt

The matching read for a message addressed to the user. Same rule: present, or refuse.

The session — six operations

04 startSession

Begin a session on one of the five lanes of chapter 5. One entry per lane, and a session can never be started without naming one.

05 endSession

Run the lane's own shut-down, clear the state derived for this user, and delete what was stored. Ends the session and forgets it.

06 restoreSession

Come back from what was stored — rebuild the signer, ask the real remote who the user is, and only then be active. What happens to an old, unencrypted record is a rule, not an accident (chapter 6, invariant 5).

07 observeSession

“Tell me every time the state changes.” It delivers the current snapshot the moment you subscribe, then one per change. This is how a screen stays in step without the module knowing what a screen is.

08 attachSigner

Use a signer that was already built, with no login at all — and it resolves the identity first, so it is asynchronous. This is the door a test walks through, and the door a host uses when it has its own key.

09 detachSigner

Let go of it, shut it down, announce that it is gone. The difference from ending a session is deliberate and small: detachSigner keeps the stored record; endSession deletes it. Letting go of a signer is not the same as forgetting the user.

Two reads a screen needs

12 currentSigner

“What is attached right now?” It answers with the signer, or refuses in a named way when there is no session. Nothing is implicitly signable: a caller that wants to sign must be able to read what it is signing with — one library quietly supplies a default here, another does not, and a module that hid the difference would make the second look like the first.

13 availableLanes

“What can this host actually offer?” — is there a browser extension, is there a relay connection, is there somewhere to store a record. A login screen builds itself from this answer instead of poking at the host's internals.

Two needs are inputs, not operations

The extension lane needs the browser extension itself handed in, and the two remote-signer lanes need both a relay connection and a clock. Those are inputs to the contract, not extra operations — which is what chapter 3 is about. One more detail with a reason: the “scan this code” lane streams its connection code to a callback you supply, rather than putting it in an observable snapshot, because that code carries a secret.

Every refusal has a name

Nothing in this contract fails with a bare string or a silent fallback. A missing session, a missing capability, a lane this host cannot offer, a transport that was not injected, a clock that was not injected, a record that will not unlock, a remote signer that took too long — each has its own named error type, so a caller can tell them apart without reading messages.

CHAPTER 03

The four ports — the module owns no environment

The single most important design fact about this module: it has no idea what kind of computer it is running on. Everything environmental is a socket the host fills in — and that is checked by a command, not asserted in a sentence.

A “port” is an ordinary idea with a slightly technical name: a plug that the person assembling the module fills in. The module says “I need somewhere to keep a small record”; the host decides whether that is the browser's storage, a file on disk, the phone's key store, or nowhere at all. The module never picks.

storage

Somewhere to keep the small record that lets a user come back without logging in again. Hand over nothing and the session lives purely in memory — and then nothing is written anywhere, which is a promise the code keeps rather than a setting it quietly ignores.

relay transport

The connection to the outside world, used by the two remote-signer lanes. The module is handed a subscription source and a way to publish, and refuses to open a relay layer of its own when it is not handed one.

clock

The source of deadlines, so a remote signer that never answers can be given up on. It is injected for a less obvious reason too: a module holding its own timers cannot be driven deterministically in a test, and a test that cannot decide when time passes cannot prove a timeout.

cryptography

Random numbers, the key-stretching function and the encryption used to protect the stored record. The floor is the module's (how many rounds, which cipher); the actual maths is the host's. A browser, a phone and a command-line tool each bring their own.

Two more things are injected rather than being a fifth and sixth “port”: the browser extension for the extension lane, and the passphrase source for unlocking a stored record. A browser extension is a host object — it only exists in a browser — so the spec hands it in as an argument, and a host without one simply does not offer that lane. That is a deliberate difference from the code this module was harvested from, which reached for the browser's global itself.

How this is checked rather than believed

The module's evidence script greps its own source and records the result with the scope written next to it. Over every TypeScript file in signer/ts/, these all read 0 lines: the browser's two key/value stores, the browser database, window., document., navigator., React, the library the architecture decision retires, and the app's own import alias @/. Restricted to the nine implementation files, globalThis, a direct crypto call, fetch, WebSocket, process., a relative escape upwards and the test runner's own module are each 0 lines as well.

Two smaller facts from the same run, because they are the kind of thing that usually leaks:

  • The module holds no timer. The only references to time in the implementation are the clock port's two member declarations and the two places the module calls them.
  • The test runner appears exactly once, and only in the tests. The five test files import the runner; no implementation file does.

Why anybody should care

Because of what it makes possible: the same module can be assembled by a browser app, a command-line tool, a phone app or a native program, and nothing in it has to change. It is also why the module can be tested at all — the whole environment a test needs is handed in, instead of being a live browser the test has to fight.

The ports are not theory, either. The module's own test support file implements all of them — an in-memory store, a clock the test advances by hand, real cryptography, and a connection whose “remote signer” is a small program running in the same process. That file is the host side of every port; it is deliberately not part of the contract, and it exists to prove the ports are real rather than to be shipped. Chapter 8 says what that leaves missing.

CHAPTER 04

The session lifecycle, as a state machine

A session is never a simple on/off. It is one of eight named states, it moves between them only along edges the spec lists, and two of those moves are refused no matter what the caller wants.

Click a state below to see what it means and where it can go next. Nothing here is hidden behind the motion — the picture and the words are the same thing.

The two moves that are refused by guard

  • Nothing becomes active without a resolved identity. The module asks the signer who the user is before it will admit to having a session. That is why an attach is asynchronous: it resolves first.
  • A second session cannot be attached while one is attached. The attempt is refused with its own named error, and the session that was already there is left untouched — a test asserts exactly that.
  • Everything the spec's list does not allow is refused too. A specific example the spec gives: a new lane started while the session is locked — the old record must be unlocked or ended first.

Three things that are read beside the state, never folded into it

Which capabilities are present

Encryption can appear and disappear independently of the state — an extension that has it, a remote signer that does not.

The identity

Present only once it has been resolved, and never inferred from a client key or a remote's own field.

What is stored

Nothing, an encrypted record, or an old unencrypted one — the third kind is what invariant 5 exists to deal with.

Why a state machine rather than a flag

The spec's own reasoning: a boolean cannot say “waiting for the person” or “there is something stored that needs a password”, and it cannot refuse a move that should not happen. Once the states are named, a screen can say something true to the user at every moment, and the module can refuse a session that would otherwise become half-attached.

CHAPTER 05

The five lanes, and what each one means for a user

A “lane” is simply a way of logging in. Five are supported, and they differ in exactly one place that matters to the person holding the phone: where the secret key actually lives.

The same five lanes, as a user feels them.
Lane Where the secret key lives What the person does What logging out leaves behind
extension In the browser add-on. Nothing secret ever reaches the app. Approves the connection once in the add-on, then approves each signature the add-on is asked for. Nothing — there was nothing of the user's to store. The lane only exists where the host hands the module an add-on.
nsec In the app, in memory, for as long as the session lives. Types or pastes the key itself. This is the lane with no safety net: whoever holds that text holds the account. The key goes when the session ends. If the host asks for a stored record, what is stored is an encrypted form, never the key.
ncryptsec In the app, but as an encrypted key — unusable without its own password. Pastes the encrypted key and its password. A wrong password fails immediately rather than hanging. Nothing is stored by this lane; the encrypted key is the user's own to keep.
bunker:// In a separate signer app. The app here never sees it. Copies a connection link out of that app and pastes it in. The link carries a secret that must match before anything binds. An encrypted session token, at most. The key never appears on this side, and neither does the link's secret in anything a screen observes.
nostrconnect:// In a separate signer app, reached the other way round. Points their phone at a code the app shows, and approves there. An encrypted session token, at most — and the connection code itself is never put anywhere a screen could log it, because it carries the secret.

What every lane shares

  • It ends in the same shape: who the user is, and the ability to sign as them.
  • Whether encryption is offered is asked of the lane, never assumed — an add-on without encryption yields a session without encryption.
  • A session can only be started by naming a lane. There is no default lane and no guessing.
  • Ending a session runs the lane's own clean-up, so a connection is closed rather than abandoned.

What only some lanes need

  • The two remote lanes need a relay connection and a clock handed in. Without them the lane refuses instead of opening a connection of its own that the host cannot see or control.
  • The extension lane needs the add-on handed in, and is offered only where the host has one.
  • Both remote lanes check the connection secret before binding — a remote signer that merely acknowledges the request is not trusted (invariant 1, chapter 6).
CHAPTER 06

The five invariants, and how each one was attacked on purpose

Five rules the module must never break. A test that cannot fail proves nothing, so each rule was broken deliberately in the real code, and the named test had to catch it — then the file was put back exactly as it was.

Invariant 1 — the connection secret is checked before binding

The rule. An unknown remote signer is never accepted just because it answered. The expected connection secret must match first, in both remote lanes. Otherwise anyone who can answer on that relay can impersonate the user's signer.

The attack. The guard that drops a bare acknowledgement was switched off in nip46.ts; the test named “a bare ack never binds an unknown remote signer” failed. Restored, fingerprint identical, green again.

Invariant 2 — the remote signer is not the user

The rule. The address of the remote signer stays separate from the address of the user. The user's identity is only ever learned by asking, never copied from the client key or from a field the remote sent.

The attack. The identity read was made to return the client key instead of asking the remote, in nip46.ts. The test named “a bound session resolves the user, not the client key nor the remote” failed. Restored, fingerprint identical, green again.

Invariant 3 — a signed record belongs to the resolved identity

The rule. A returned record must verify cryptographically and carry the same address that was just resolved. A perfectly valid signature from a different key is refused.

The attack. The comparison was disabled in capability.ts. The test named “signEvent fails closed when the returned event pubkey differs from the authenticated identity” failed. Restored, fingerprint identical, green again.

Invariant 4 — encryption is optional, and never invented locally

The rule. If the signer does not provide an encryption scheme, the module must not compute it — not from a key the user never exposed, and not by pretending a method exists.

Two attacks, both real but only one usable as evidence.

  • The permission list that gates the capability set was made to let everything through, in capability.ts. The test “the composer allow-list gates the capability set — absent means refuse, never synthesise” failed. Restored, fingerprint identical, green again. This row holds.
  • The extension lane was made to manufacture an encryption capability the add-on did not have, in lanes.ts. This row does not hold: the run reports the test command failing, but the output shows the test was never found — the name filter matched no test, before the change and after the restore alike. The mutation is real; the evidence that it was caught is not there. Chapter 8 states it in full.

Invariant 5 — a stored session is never silently plain text

The rule. What is stored is encrypted, or nothing is stored. An old unencrypted record is migrated on request or forces a deliberate log-in again — never kept quietly. And because the stored round count is something an attacker can edit, a record claiming too few rounds is rejected before any key is derived.

Two attacks, both holding. First, the round-count floor was disabled in vault.ts; the test named “iteration-downgrade tamper” failed. Second, the session was made to store the raw session token instead of its encrypted envelope, in session.ts; the test “a bunker session is written encrypted, and endSession clears it” failed. Both files restored, fingerprints identical, both green again.

And the fingerprints are still right today

I recomputed the five fingerprints from the files as they are on disk now and compared them with the values the falsification run recorded before it touched anything: all five are identical (nip46.ts, capability.ts, lanes.ts, vault.ts, session.ts). So the “restored byte-for-byte” claim is not just a line in a log — the files on disk right now are exactly the files the measurements were taken from.

CHAPTER 08

What is not yet true

This chapter is deliberately uncomfortable. Everything below is a limit of the module as it stands, taken from the build's own record of what it did not verify — not a caveat, and not softened.

1 · No host adapters ship at all

The module delivers no implementation of the storage port, no implementation of the cryptography port, and no relay connection. That is deliberate — they belong to whoever composes it — but the consequence is plain: the only working implementations of the four ports are the ones inside the module's own test support file, which is not part of the contract and was never written to be shipped. Nobody has ever run this module against a real host's storage, a real host's cryptography or a real relay layer. A composer must write all four before the first real login is possible.

2 · No relay has ever been contacted

The two remote-signer lanes were driven against a small signer emulator that runs inside the same process. No network was involved. So everything that only shows up over a real connection is untested: a slow relay, a dropped connection, a signer that answers in a slightly different shape, a relay that repeats a message. The app's own end-to-end tests are what cover that today, and they are not reachable from this build.

3 · One signature deviates from its own spec

The spec says an already-built signer is attached with attachSigner(signer, settings) — settings given at the moment of attaching. The implementation takes attachSigner(capability, { lane }). The settings this module defines are the composer's and are set once when the session is created, so a per-attachment settings override is not implemented; the second parameter carries only the label the snapshot reports. Someone implementing from the spec will write a call the code does not accept.

4 · Portability is unproven, and one implementation cannot prove it

The whole reason for writing a spec before a second implementation is that a Rust, Flutter or Angular version should be able to meet it. None of them exists, and nothing here demonstrates that the spec is portable. That claim is a claim. (One thing the spec does handle: a browser extension only exists in a browser, so the spec makes the extension lane's transport something the host hands in — a host without one simply does not offer that lane.)

5 · Compatibility with the app's existing stored records is judged, not measured

Will a user who is already logged in on the app be read correctly by this module? The reasoning is that the stored format's keys and construction are unchanged and the encoding is standard — but no record written by the app was available to read here, so this has never been observed. It is a judgement, and the first real consumer is where it gets tested. Until then, treat it as unknown.

6 · One of the seven “prove the test is real” rows does not hold up

Chapter 6 described the method: break a rule, watch the named test fail, restore the file. Six of the seven rows show exactly that. The seventh — invariant 4's extension lane — does not, and here is the output verbatim from the recorded run:

error: regex "leaves nip04 and nip44 absent when the extension lacks them (fail closed)" matched 0 tests. Searched 1 file (skipping 19 tests) — exit 1.

The command exited non-zero, and the routine counts any non-zero exit as “the named test failed”. But that output says the test was never found by the name filter, and the same command on the restored file exits non-zero in exactly the same way — so the recorded run shows no green confirmation either. I reproduced this on the untouched files today: the same filter still matches nothing and still exits 1, while a shorter filter runs the very same test and it passes.

What that means, stated exactly: the mutation is real, the test exists and passes normally, and the evidence that this particular mutation is caught by that test is absent. Invariant 4's other half (the permission list that gates encryption) is properly falsified and does hold.

7 · Two smaller things, read from the code rather than measured

  • The market's own test suite was never run in this build — neither required nor attempted. The isolation checks are what stand in for it, and they show the module does not reach into the app.
  • The table of allowed state transitions in the code is slightly wider than the spec's list. Reading session.ts, four moves are permitted that the spec's own list does not name: idle → restoring, idle → closing, connecting → idle and awaiting_user → active. I read them; I did not test them, and nothing in the evidence covers them. Deciding whether the spec or the code is right is a decision for you, not a defect I should have quietly fixed.

The honest sentence for all of chapter 8

The module's contract, its five lanes, its state machine, its five invariants and its isolation are written down and executed — 79 green tests and one falsification row short of complete. What is missing is not effort: it is a host, a relay, a consumer and a second language. Until those exist, this is a proven design and unproven software.

CHAPTER 09

Open questions, and the assumptions I had to invent

Four questions the spec deliberately leaves open for you, and — separated out, so nothing is buried in the prose — the place-names, translations and guesses this page makes on your behalf.

The four questions the spec leaves open

1 · Is the stored format contract, or just its floor?

The module writes and reads a stored record, and its floor (how many rounds of key stretching, which cipher) is already contract. The open question is whether the whole shape — the field names, the layout — is frozen too. The spec's lean: freeze the format, but leave the names to the host, so a host that already stores something else is not forced to adopt this one's.

2 · Should the scan-a-code lane remember a session?

One remote lane stores a session so the user does not have to reconnect. The other currently stores nothing until the connection is confirmed. Whether an unconfirmed one should ever be remembered is a product question about what “remember this signer” means — not a code question.

3 · What may a host do with the connection code?

That code carries the secret, so it is delivered straight to a callback and never put into an observable snapshot a screen could log. Whether it should instead be handed over as an opaque token that a screen cannot log is a question for the first real consumer.

4 · Where does the second implementation go, and what proves it?

A native or mobile implementation would be the real test of this spec's portability. Nothing in this build demonstrates it, and the spec says so in as many words: the claim is a claim.

What I invented, and want you to correct if it is wrong

None of the following is in the spec. Each is a decision I made to turn a technical document into something readable, and each is the kind of thing that should be corrected in one line rather than argued about:

  1. “The module” means the spec and this implementation together. Where the two could be confused I say which one I mean. The spec is the authority; the code is its first implementation, and it is the only one.
  2. Every plain-language gloss is mine. The ones most likely to be wrong: record for what the code calls an event; lane for a way of logging in; port for a socket the host fills; adapter for a host's implementation of a port (a word the code does not use); fingerprint for a sha256 checksum; the seam for the boundary where a capability is defined. The protocol numbers (NIP-07, NIP-46, NIP-49, NIP-04, NIP-44) are given as one-line meanings rather than as specifications.
  3. The grouping of the thirteen operations into five bands — identity, signing, encryption, session, reads — is mine. The spec lists them flat.
  4. The state-machine picture is my drawing. The spec carries the same machine as text, and its code-block diagram lists one edge (restoring → locked) that its prose list does not. I drew the union of the two and said so in chapter 4's footnote; the four extra moves the code allows are recorded in chapter 8.
  5. “0 reported failures” — that wording is deliberate. The falsification script counts any non-zero exit as a failure, and one row's non-zero exit came from a test filter rather than a failing assertion, so the honest number is “0 reported” and the honest note is chapter 8's.
  6. I chose the balance of this page: the measured wins are given the numbers they earned, and the gaps are given a whole chapter and the last word. If that balance is wrong for you, the balance is what to change — the facts are the artifacts'.
  7. Every number on this page is quoted from the module's evidence files (evidence/record.md, 01-build-and-tests.txt, 02-invariant-falsification.txt) rather than recomputed by me, with three exceptions that I did check myself: the five file fingerprints in chapter 6, the exact dependency version, and the one failing test filter in chapter 8. I did not re-run the whole suite to reproduce the 79/222 totals from scratch.
  8. I assumed you would rather read one honest page than four cautious ones — so where the record says “judged, not measured”, this page says “judged, not measured” rather than “assumed compatible”.
