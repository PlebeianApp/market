CHAPTER 01

What the module is, and why it exists

A composition that knows both tiers — the store's local endpoint and the relay seam — and is the only module that does. Neither of them knows the other exists.

The job, in one sentence. Answer a caller's event operations — query, subscribe, publish, count, delete and the {events, complete} envelope — over the store's local endpoint and the injected relay seam, merging them local-first with one declared write-back policy, and reporting, honestly, whether the answer is complete.

Where it came from. The spec was written at its final state — the module as it should be, not as it is today. The TypeScript implementation in ts/ is the first one, written in the same run the spec was frozen. What it replaces is a decision nobody owned: the write-back was scattered — 4 of 11 loader modules in the vendor's own ecosystem applied it, and each market read site decided the local-first sequence for itself. One declared owner is better than a convention every call site remembers.

What this module is not

It is not the store — it never opens a database, never keeps a cache, and never decides what to evict. It is not the relay seam — it holds no socket, owns no relay handle, and never decides which relay a read reaches. It is not a filter validator — the fail-closed predicate is the store's and is reached by calling the endpoint's read, not by growing a second predicate here.

CHAPTER 02

Two tiers, one answer

The local store answers first; the seam's fill follows. The events are merged into an id-unique union with per-id provenance, and the answer reports whether it is complete.

The local-first sequence. On the default path P1 (query{localFirst:true}), the endpoint's local read answers first. The upstream seam is then asked for the fill — events the local store does not yet have. The fill's events are written back into the store (the write-back policy, chapter 4) and both sets are merged into one id-unique answer. On P2 (query{localFirst:false}) the fill is attempted first, then merged; the merge order inverts but the provenance rule does not move with it — an id the local read carried is 'local' on both paths.

What provenance means, and what it does not

Provenance is per answer and per id — a declared companion read originOf(answer, id) returns 'local' or 'network'. It is not a flag mutated on a shared event instance (the vendor's sticky-bit defect, which this module exists to avoid). And the envelope is deliberately not widened to {events, complete, origins} — that is mentioned as an open question, not taken.

CHAPTER 03

Six operations, seven named paths

Five NIP-01 verbs plus the {events, complete} envelope, and each operation has exactly one named path — P1 through P7 — that says how things happen and in what order.

The path explorer below shows the call order for the two query paths — and how the repair changed P2.

P1 · query{localFirst:true}

Call order: read → query → write, then merge (local first in the answer). The endpoint's read answers first (LF-1); the fill follows; the fill's events are written back (LF-2); the id-unique union and provenance are recorded. complete is a fact about the wire's boundary.

Three more operations

publish

Writes locally before any relay attempt. The local write's outcome is reported as stored; the relays' own answers fill accepted and refused.

count

Never fetches. Counts through the store's own index and reports approximate: false. The wire's NIP-45 count belongs to the seam.

delete

Routes through the endpoint's removal, and the resulting change reaches every open subscription on the change fan-out. The three kinds of deletion are the store's rule, not re-decided here.

CHAPTER 04

The one accept gate, applied at three destinations

One declared, inspectable hook — the accept? member of the write-back policy — applied at the three destinations and nowhere else. Absent means accept everything, which is validation's pass-through default.

The gate is given each candidate event, the flow it is applied for ('read' or 'publish'), the endpoint's declared tier, and a resolver so a link rule can reach a referenced event. It answers 'accept' or 'reject'. It is bounded by the flow's own wall-clock budget: a hook that has not answered within the budget drops its candidate, and a dropped event is not an incomplete answer — complete stays a fact about the wire's boundary.

Click a destination below to see what the gate is given and what it decides there.

A · The store write

Content arriving off the seam port and headed for the store — a query's fill and a subscription's fill — passes through the one rule at the store-write boundary (acceptForStore) once, before the union, and the accepted set is then routed on to the consumer as well. The gate sees operation: 'read' and the endpoint's declared tier.

The gate is also how validation would compose: validation presets supply the accept hook, absent means pass-through, and no second accept rule is ever grown inside this module. Today, the hook is absent by default and nothing supplies it — the validation module exists and has its own suite, but nothing here imports it.

CHAPTER 05

The bounds it refuses to cross

Four boundaries that the module must never cross, and the completeness rule it must never violate. Each was checked by a command, not asserted in a sentence.

The filter predicate. A malformed identity filter — { ids: ['not-a-hex-identity'] } — is rejected before it reaches either tier. The predicate is the store's single implementation, reached by calling the endpoint's read, and no second predicate is grown here. On P2 this was not always true: a blind wave found the malformed filter reaching the wire and a write behind the refusal. The repair moved the ordering — the endpoint's read now runs before both tiers on every read path.

CHAPTER 06

How the rules were attacked — the story of the block

40 deliberate mutations, each breaking one rule in a real file, each making its named test fail, each restored byte-for-byte. And the one path that was not measured — and what happened when a blind reviewer found it.

The blind wave that blocked this module

On 2026-09-30, two blind reviewers, Red Team A and Red Team B, independently attacked the repaired I2 candidate (db5a3a3). Both found the same defect: on the normative path P2 (query{localFirst:false}), a malformed identity filter reached the wire before the endpoint's read could reject it — and the seam's answer was written into the local store behind the refusal. RT-A returned MICRO_HARDEN. RT-B returned BLOCK.

The repair. The ordering moved, not the sentence. The endpoint's read was hoisted above both tiers and every write-back, on every read path — so a refusal now reaches the caller with no side effect behind it. P2 kept its network-first merge order, its both-tier provenance rule, and its LF-5 behaviour. The frozen statement #f775fb was not amended: the code changed instead.

A third blind reviewer returned CLEAR. Red Team C (RT-C) re-verified the repair and independently reproduced the suite (37 pass at that tree), the checkers, and the falsification harness. One MINOR finding — two docstrings the repair had made untrue — was fixed in a follow-up commit (6cb50bb).

Then a regression the store shrink caused was found by measurement. After the store shrink landed (I3), a subscription the caller had opened with {kinds:[1]} was receiving a local write of kind 7 — because the endpoint's changes is unfiltered, and the store's own live path had previously applied the filter. This module applies the subscription's own filters to every change-stream event before delivery, and that is measured (mutation 33 in the falsification table).

CHAPTER 08

What is not yet true

This chapter is deliberately uncomfortable. Everything below is a limit of the module as it stands — not a caveat, and not softened.

1 · Nothing imports this module

No module in the assembly lists event-access in its needs: declaration, and no import specifier in any file reaches it. The module's own contract is declared; nothing yet exercises it for real.

2 · Both ports are hand-written fakes

The store endpoint and the relay seam are implemented inside ts/harness.ts — in-memory fakes that record calls and return scripted answers. The store's own endpoint now exists in event-store/ (increment I3 landed 2026-09-30), but nothing here is wired to it — the module still runs only over these hand-written fakes — and no real relay connection was ever opened.

3 · Validation's accept hook is not wired in

The gate accepts an optional AcceptHook. When absent — which is the default — everything passes through. The validation module's job is to supply such a hook with its presets, but nothing in this assembly wires them together. The validation module exists and has its own 32-case suite; it is just not plugged in here.

4 · Two readings remain open

The change pump is never torn down (by design; the port's changes is endless), and the withDeadline helper strands the pending upstream promise when the deadline wins (bounded and unobservable at this increment). Both are disclosed in the freeze note; neither is a code defect.

CHAPTER 09

Open questions, and the assumptions I had to invent

Four questions the spec deliberately leaves open for you, the decisions this page makes on your behalf — separated out, so nothing is hidden in the prose.

1 · Should provenance move into the envelope?

The spec keeps a companion read originOf(answer, id). A third envelope member {events, complete, origins} would save one call per event and widen a shape another spec already states. Not taken; open for you.

2 · Should count ever consult the wire?

It does not today — M14, D-O4. The wire's NIP-45 count is available on the seam for a caller that composes nostr-io alone. That alternative is not lost; it is one call away.

3 · Where does the excluded list come from?

The wallet rule arrives as an input to the excluded list. If a host ever supplies two exclusions, a nicer shape may be needed. Today one declared value suffices.

4 · What is persist:false's scope?

It suppresses the write-back for that call only. The answer is unchanged and originOf still reports network. The alternative — per-call exclusions — is named and not taken.

What I invented, and want you to correct if it is wrong

  1. “The module” means the spec and this implementation together. The spec is the authority; the code is its first TypeScript implementation.
  2. Every plain-language gloss is mine. Fill for the seam's answer; gate for the accept hook; path for a named route through the composition; seam for the boundary between tiers; fork for the localFirst branch.
  3. The grouping of the operations into five bands — reads (query/subscribe), write (publish), local (count/delete), pointer (P5) — and the envelope separate.
  4. The gate's three destinations as an explorable panel is my reading of the spec; the spec prints the three destinations in prose.
  5. Every number on this page is quoted from the module's evidence captures (01-build-and-tests.txt, 02-invariant-falsification.txt). None was recomputed by me.
  6. I chose the balance of this page: the measured wins are given the numbers they earned; the gaps are given a whole chapter and the last word. If that balance is wrong for you, the facts are the artifacts'.
