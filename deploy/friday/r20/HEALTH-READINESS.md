# R20 health readiness input and boundary

This source change is an ingress availability gate. It does not change consensus acceptance or prove private rehearsal, mint conformance, release acceptance or public activation.

`POC_FRIDAY_BROWSER_READY=true` is still an explicit operator enable. Both the Go site and authority now additionally require runtime readiness. The authority collects request-time observations with one 5-second monotonic deadline. Each signer gets 2 seconds; three authenticated ready participants suffice even if the fourth hangs. Two strictly increasing canonical heights separated by at least one second are required after startup or degradation. Equal height expires after 20 seconds measured from the start of the last progress observation. Identity mismatch, stale/future observation, clock regression, timeout, mint failure or signer threshold loss resets warmup. These fixed engineering defaults are not owner-approved performance SLAs.

The authority's independently reviewed mint input is `/etc/plebeian-auctions-friday/health-r20-pins.json`: root owner, runtime service group, regular single-link mode 0640, opened without following a symlink, at most 16 KiB. Both site and authority receive its exact SHA-256 through `POC_FRIDAY_HEALTH_PINS_SHA256` in the root-owned environment. Missing/invalid input keeps new admissions disabled. The inert example contains placeholders and is not deployable.

The input pins deployment, chain, genesis, validator roster, committee keyset/version, DKG run, public package, signer roster and canonical mint URL. These must equal fixed authenticated runtime configuration. Mint public key, active sat keyset, denomination-key digest and server version must equal current responses on the fixed mint transport; exactly one active zero-fee sat keyset and required NUT advertisements are also required. This checks metadata on the existing trusted local mint route. It is not a cryptographic proof of the mint process's identity, spend enforcement or continuing integrity. The conformance receipt hash is an independent release attestation reference. Review must establish its contents, exact runtime/transport ownership, and binding to this mint/keyset before installing the health input. Advertising NUTs alone cannot close MINT-001. The active keyset and complete FundingAbort payment domain are also checked against current authenticated canonical application state; inconsistent bootstrap/browser/config provisioning must be rejected during integration.

Signer status uses a domain-separated signed coordinator challenge and signed response bound to participant, deployment/network/mint/DKG pins, durable journal binding and the same live terminal process instance as SignerRPC. Health and terminal transport share one immutable enrollment capture. Health requires exact epoch equality: a newer or older reply is unready and is rejected before coordinator anchor observation. A signed false response makes no coordinator observation. Positive exact-binding health remains a stateful authenticated observation: it can initialize the accepted epoch/process and checks the existing coordinator anchor, but cannot adopt a newer epoch or refresh a transport. The existing coordinator generation/epoch/process anchor rejects replacement and reused epochs. A restarted signer that no longer matches the active binding remains unready until separately reviewed reconstruction/re-enrollment; health does not perform it. A status probe only asserts binary, Rust, proof-use, admission and RPC journal safety. It does not generate nonces, claim signing requests, advance signer journals or clear quarantine. Coordinator monotonic observations can advance the existing coordinator anchor, as existing SignerRPC does.

New funding preparation and seller intent are blocked on degradation. Funding confirm can run only for a durably recorded broadcasting/broadcast/admitted row; merely prepared or signed rows cannot broadcast. Seller registration during degradation requires an existing recorded challenge through the same recovery classifier. Terminal reads/acknowledgements, funding status, browser deployment/seller reads and exact FundingAbort routes retain existing validation. They gain no capability to override signing policy, mint checks, finality, origin, proof identity or journal safety. A stalled chain or unavailable mint may prevent a recovery operation from completing; it does not erase its journal or disable read/retry routing. A valid health input supplies the active mint keyset for recovery startup without requiring a reachable mint. Without that input the old startup compatibility path still requires live mint discovery, while new admission stays disabled.

The Go site checks a fresh bounded status response only from fixed loopback authority port 8181, matching its independently pinned health-input digest and browser/network pins. Both browser readiness booleans and direct R20 event/close broadcasting use the same decision. Health preflight is inside the existing 20-second site transaction budget, preserving the reviewed 25-second closer HTTP/30-second outer budgets. Site reads remain available. Existing explicit recovery-only mode still blocks every site mutation; exact authority recovery stays separate.

Raw Comet RPC and FIPS signer/mint ports remain restricted deployment interfaces. This patch does not add a consensus health rule to `CheckTx`/`FinalizeBlock`, or promise to gate a separately exposed raw RPC endpoint. Independent review must verify there is no public direct-to-Comet admission route.

Remaining gates: A3 review, reconcile the small read-only anchor API addition with the signing lane, produce one successor freeze, exact B1/B2, independently reviewed mint health input/conformance and transport ownership, fresh DKG/genesis/pins, real FIPS signer probes and clock-skew bounds, one-validator-down progress, one/two-signer-down and hung-signer behavior, mint outage/restart, and full refund/settlement restart/lost-response rehearsal. No host action is authorized by these files.


## R2 review repairs

Health never adopts a newer signer epoch on behalf of an older active terminal transport. The immutable enrollment captured by participant composition is shared with health; different epochs fail before coordinator observations. Signed false performs no coordinator observation. Positive exact-binding observations remain stateful, including same accepted epoch/process initialization; cancellation is checked around observation awaits. No signing journal, anchor or transport is reset/refreshed.

The live reader now uses the same supported-capability parser as the SIG_ALL mint adapter. NUT-04 requires explicit `disabled=false` plus a `bolt11`/`sat` method; NUT-07/09/10/11/12 require explicit `supported=true`. Missing, malformed and negative mandatory settings are not support. Capability restoration must pass two new advancing health observations. This does not replace independent mint identity/conformance review.

The ordinary UI resamples readiness and independently loaded release pins on its existing refresh/login path. One coalesced request has an eight-second deadline. Any valid independently pinned response (ready or not ready) resets failure backoff and permits the next request four seconds from the previous request start. Transport/identity-fetch failures back off 4/8/16/30 seconds, capped at 30 seconds; the first valid response returns to short cadence. Backoff uses the browser monotonic clock when available. There is no extra background polling loop or unlimited login bypass. Late responses cannot re-enable controls after a timed-out check. Both server readiness booleans must explicitly be true, recovery-only false, and runtime identity/funding-policy digest must match the independently validated release pins.

Readiness transitions revoke any seller consent/cancel pending approvals through the accepted seller UI's existing hook. A release-identity change retires the prior controller/actor generation and requires explicit reconnect, retaining the existing in-memory signer so automatic invalidation does not discard a tab-local private identity; restoration does not revive consent. The separate compatibility overlay applies exactly this health edit to the frozen accepted CFG/PAY R2 UI, preserving its wallet lease and maintenance scheduler. It is a required later integration edit, not a merge of PAY source into the HLT patch. Rerun consent/cancellation/serialization acceptance on the eventual combined freeze.

Existing connected controllers retain normal passive import/status recovery while new admission controls are disabled. This source does not introduce a fresh-tab degraded recovery connector, waive independent pins, or enable new funding during degradation. A new/reloaded tab waits for verified readiness to recover before ordinary connection; any requirement for immediate fresh-tab degraded wallet access needs a separately scoped recovery-only connector and real browser/mint acceptance. No source-level route test is a claim of successful live recovery.


## R3 timing contract (HLT-A3-02)

The R2 30-second retry for a valid not-ready response exceeded the backend 20-second continuity window, so a sole tab could remain warming forever. R3 changes only UI scheduling: no backend freshness/progress/threshold rule is relaxed, and no background readiness observer is added. A valid independently pinned response means the request worked even if dependencies are unready. Such responses reset transport failure backoff and schedule four seconds from request START, not completion. Only transport/identity-fetch failures keep exponential cooling. Requests remain coalesced and their starts are at least four seconds apart.

The named contract is the existing active four-second UI interval, finite eight-second UI request and five-second backend collection bounds, plus backend sample spacing/age and twenty-second continuity. Request-start spacing avoids adding a response-duration cooldown to each observation. A sole active tab can perform two healthy observations without requiring another client to warm readiness. Real browser suspension or unbounded scheduling/transport delay cannot promise readiness; when execution resumes, fresh observations remain necessary. These are engineering limits, not an owner-approved latency/capacity SLA.

Coupled fake-clock tests exercise the actual UI timers and actual backend readiness probe for prolonged dependency and HTTP outages, sole/multiple clients, slow collection and asymmetric transport within the existing bounds, renewed failures and true stopped height. Consent/cancellation, independent pins and connected recovery behavior remain unchanged. Combined SEC/PAY integration and live browser scheduling/load/outage acceptance remain reserved gates.
