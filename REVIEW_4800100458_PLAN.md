## Blocking 1 — Authenticate events before parsing/buffering
*(signature ✅ via `cd8b97a0`; authorization-before-mutation ❌ — inlines 4800101759, 4800105709)*

`subscriber.ts` now calls `verifyIncomingEvent` (sig + id) for all four
kinds. What's missing is **authorization before state mutation**, plus
re-authorization on replay, plus negative coverage.

### Gaps
- `onPathReleaseEvent` calls `recordPathRelease(...)` **before** the
  referenced bid is resolved and the signer is authorized. A correctly
  *signed* third-party kind-1025 overwrites an honest bidder's selected
  release (single slot per bid), then later produces `fraudulent_bid`
  against the victim. `validatePathRelease` does check
  `release.bidderPubkey === bid.bidderPubkey`, but only at verdict-derive
  time — by then the wrong-author event has already clobbered state.
- `onSettlementEvent` calls `recordSettlement(...)` before verifying the
  authenticated signer is the auction seller; the single settlement slot
  can be overwritten by a correctly-signed non-seller event.
- Buffered events (`pendingReleases`, `pendingSettlements`) are replayed
  via `drainPending`→`onPathReleaseEvent`/`onSettlementEvent`; any
  authorization added must also be re-applied on replay.

### Changes
1. `state.ts` — make `recordPathRelease` return a richer result
   (`{ auctionState, bidState } | { reason: 'unknown_auction' | 'unknown_bid' | 'wrong_author' } | null`)
   and **reject** the write when `release.bidderPubkey !== bid.bidderPubkey`
   (store nothing, do not update `pathReleases`/`pathReleaseObservedAt`).
2. `state.ts` — make `recordSettlement` reject when
   `settlement.sellerPubkey !== auctionState.auction.sellerPubkey`
   (do not overwrite `auctionState.settlement`).
3. `subscriber.ts` — on rejection from `recordPathRelease`/`recordSettlement`,
   drop the event (log at warn) **without** buffering wrong-author evidence
   and **without** changing reputation/publishing a verdict. Only buffer
   when the failure is `unknown_auction`/`unknown_bid` (i.e. ordering, not
   auth).
4. Re-authorization is automatic because `drainPending` re-enters the same
   handlers.

### Negative coverage (`auctionValidatorSubscriber.test.ts`)
- Validly-signed kind-1025 from a non-bidder pubkey: assert
  `pathReleases` unchanged, no verdict published, no `fraudulent_bid`.
- Validly-signed kind-1024 from a non-seller pubkey: assert
  `auctionState.settlement` unchanged and no `settled_*` published.
- Both cases replayed through `drainPending` after the auction/bid lands.

## Blocking 2 — Require every expected proof to be spent
*(❌ — `aggregateProofStates` returns `spent` if ANY proof is spent)*

`state.ts` `aggregateProofStates`: `if (snap.state === 'spent') return 'spent'`
short-circuits on the first spent proof. `deriveSettlementVerdict`
(lifecycle.ts) gates `won_pending_settlement` on
`aggregate !== 'spent'`, so a *partial* spend passes the gate. The
settlement-completeness layer (`validateSettlementLegNut7States`) does
enforce per-proof spent, but the aggregate semantics are misleading and
the reviewer wants them fixed at the source.

### Changes
1. `state.ts` `aggregateProofStates` — redefine `spent` to require **every**
   expected `proof_y` present and explicitly `spent`. Mixed states:
   - any spent + any unspent/missing/pending/unknown → not `spent`
     (return `pending` if all remaining are pending/unknown and none
     missing; `unknown` if any unknown; `missing` if any missing).
   - Update the doc comment block accordingly.
2. `lifecycle.ts` `deriveSettlementVerdict` — the gate
   `if (aggregate !== 'spent') return won_pending_settlement` now correctly
   holds until truly complete redemption. No other change needed there, but
   audit `derivePreCloseVerdict`→`validateBid`'s fraud detection: pre-close
   "any proof spent ⇒ fraudulent" must remain valid. If `validateBid`
   relied on aggregate `spent` meaning "any", add an explicit
   "anySpent" path in `validateBid` (or pass per-proof states) so
   pre-close fraud semantics are preserved while settlement uses
   all-spent. Confirm against `auctionBidValidation.test.ts`.

### Negative coverage (`auctionValidatorLifecycle.test.ts` / new
`aggregateProofStates` unit test)
- 4 expected proofs: {1 spent, 3 unspent} → aggregate `pending`/`unknown`,
  verdict stays `won_pending_settlement`.
- {2 spent, 1 missing, 1 unknown} → not `spent`.
- {all spent} → `spent` → proceeds to settlement completeness.
- {all unspent} → `unspent`.

## Blocking 3 — Use validator-observed release timing
*(✅ `9bb28bfd` added `pathReleaseObservedAt`; ❌ atomicity gap — inline 4800102881)*

`state.ts` `recordPathRelease` stores `pathReleases[bidId]` (overwritten
each arrival) and `pathReleaseObservedAt[bidId]` (min preserved). A later
valid release **inherits** a different earlier event's `observedAt`, so a
backdated/late release can be classified as prompt using an unrelated
event's timestamp.

### Changes
1. `state.ts` — bind the selected event and its `observedAt` **atomically**.
   Either:
   - store `pathReleaseObservedAt` keyed by **release event id** (not bid
     id), and resolve the observed time through the selected release's id;
     or
   - store a single `{ release, observedAt }` object per bid and replace it
     only when the new release wins a **deterministic selection** (e.g.
     earliest `created_at`, tie → lex event id) — never merge the new event
     with the old `observedAt`.
2. Define the deterministic selection rule in a named helper (e.g.
   `selectCanonicalPathRelease(a, b)`) and unit-test it.
3. `lifecycle.ts` `deriveSettlementVerdict` — read the observed time that
   belongs to the **selected** release (not the bid-wide min).

### Negative coverage
- Early unusable release (wrong-author or invalid derivation) observed at
  T0, then a distinct valid late release observed at T1≫T0: assert the
  selected release is the late one and its `observedAt` is T1 (prompt/late
  classification uses T1, not T0).
- Two valid authorized releases: assert deterministic selection picks the
  same one regardless of arrival order.

## Blocking 4 — Make post-grace redemption observable
*(✅ `b654e493` added `refreshBidChain`/`refreshAuctionReleasedNonterminal`; ❌ no retry on unknown, poller still excludes post-grace — inline 4800108731)*

`state.ts` `collectLiveBids` skips every bid once
`now > maxEndAt + settlementGrace`, so `voluntary_late` releases and later
redemptions (which happen *after* grace) are never polled by `tick()`.
The new refresh helpers issue **one** query; an `unknown` result (transient
mint failure / propagation delay) schedules no follow-up, leaving a
released nonterminal bid stuck indefinitely.

### Changes
1. `nut7Poller.ts` — add a **bounded post-grace retry** path with backoff
   and an explicit cutoff:
   - Track per-bid `postGraceRetry: { attempts, nextAttemptAt }` (on
     `ValidatorBidState` or a poller-local map).
   - When `refreshAuctionReleasedNonterminal`/`refreshBidChain` returns
     `unknown` for a released nonterminal bid, schedule a follow-up with
     exponential backoff up to a max attempts / hard cutoff (document the
     stopping condition: e.g. max attempts or a wall-clock cutoff after
     `maxEndAt + settlementGrace + C`).
   - Lift the `collectLiveBids` post-grace exclusion for released
     nonterminal bids (or drive them solely via the retry scheduler).
2. `state.ts` `collectLiveBids` — keep skipping terminal bids but **do
   not** exclude released nonterminal bids solely because `now > grace`.
   Either relax the guard or document that the retry scheduler owns them.

### Negative coverage (`auctionValidatorNut7Poller.test.ts`)
- First post-grace refresh returns `unknown`; a later **scheduled** retry
  (advanced clock, no new relay event) returns `spent` → verdict flips to
  `settled_*`.
- Backoff respects max attempts → after cutoff the bid is left at its
  last verdict (no infinite loop).

## Blocking 6 — Wire close-role assignment into production (or narrow claims)
*(✅ `7561eb8a` wired `assignCloseRoles` into `publishIfChanged`; ❌ one-shot + null-role winner risk — inline 4800106841)*

`publisher.ts` calls `assignCloseRoles` once (gated on `closeHandled`),
only marking bids currently `valid_bid_placed`. A bid that is **pending at
close** but flips to `valid_bid_placed` *after* close (late NUT-7) keeps
`postCloseDecision === null`; `deriveVerdict` then treats
`postCloseDecision !== null || currentClaim === 'valid_bid_placed'` as
"wasValid" and routes a **null-role** bid into the winner branch.

### Changes
1. `lifecycle.ts` `deriveVerdict` — guard the winner path: a bid with
   `postCloseDecision === null` must **not** be processed as a possible
   winner. Add an explicit branch: if `currentClaim === 'valid_bid_placed'`
   but `postCloseDecision === null` after close, re-run
   `assignCloseRoles`-equivalent role assignment for the newly-valid bid
   (deterministic snapshot/recompute), or hold it at a non-winner claim
   until roles are assigned.
2. Define deterministic snapshot semantics: decide whether
   `assignCloseRoles` is a one-shot snapshot (only bids valid *at* close
   can win) or recomputed (late valid bids can win). The reviewer asks to
   "define deterministic snapshot/recomputation semantics" and ensure a
   null role cannot enter winner settlement. Pick one, document it in the
   ADR, and enforce it.
3. If recomputed: re-run role assignment (ungate it for the newly-valid
   bid, or make `assignCloseRoles` idempotent and re-runnable) before
   settlement processing.

### Negative coverage (`auctionValidatorPublisher.test.ts` /
`auctionValidatorLifecycle.test.ts`)
- Composed pending-at-close → valid-after-close: a bid pending at
  `maxEndAt`, then NUT-7 flips it to `valid_bid_placed` after close.
  Assert it does **not** become a winner with a null role (either it is
  re-role'd deterministically or held at a non-winner claim).

## Blocking 7 — Pin updates to the original addressable auction identity
*(✅ `228184a2` added `sameAuctionIdentity`; ❌ coordinate-based lookup missing — inline 4800107831)*

`state.ts` `upsertAuction` keys state by `auction.rootEventId`. A normal
**addressable replacement** carries a *new* event id and no
`auction_root_event_id` tag, so `parsed.rootEventId` equals its own new
id → `state.auctions.get(newId)` is undefined → inserted as a **second**
auction; the `sameAuctionIdentity` guard never runs.

### Changes
1. `state.ts` — resolve replacements by **canonical coordinate** first:
   - Add `auctateByCoordinate: Map<coordinate, rootEventId>` (or scan
     auctions for a matching `coordinate` + `sellerPubkey` + kind).
   - In `upsertAuction`, if no entry exists under `auction.rootEventId`,
     look up by `auction.coordinate` (and matching seller/kind). If found,
     treat as an update to the existing pinned auction and run
     `sameAuctionIdentity` against the stored `rootAuction` (which still
     must match seller, `d`, coordinate, kind, pubkey). **Retain the
     pinned first event id** as `rootAuction` even as `auction` refreshes.
   - Handle restart recovery: since state is memory-only and rebuilt on
     subscribe, ensure the first-seen event for a coordinate becomes the
     pinned root (relay `since` window already re-fetches history).
2. Keep the existing immutable-fields check; reject mismatches.

### Negative coverage (`auctionValidatorContext.test.ts`)
- Same coordinate, new event id, **no** `auction_root_event_id` tag,
  same seller: assert the existing auction state is **updated**, not
  duplicated; `state.auctions` still has one entry pinned to the original
  root id; accumulated bids/settlement preserved.
- Different valid signer or coordinate: assert a second state entry is
  not created / cannot replace the pinned auction.

## Inline 4800109930 — Harden mint reachability probing (SSRF/concurrency)
*(❌ — `mintReachability.ts` eagerly probes every mint, no policy)*

`refreshAuctionMintReachability` probes every seller-provided mint URL
eagerly in `onAuctionEvent` and on every `tick()`. `checkMintReachability`
has a timeout but no destination/redirect policy, private-network
protection, mint-count cap, or global concurrency/backoff.

### Changes
1. `mintReachability.ts` — disable **eager** probing by default (or gate
   it behind an operator-controlled outbound-network policy). Make
   reachability **lazy/per-bid**: only probe a bid's selected mint when
   that bid is actually live, not every mint for every auction every tick.
2. Add an outbound-network policy (`policy.ts` already exists — extend
   it): allowlist/denylist for destinations, block private/link-local
   ranges, cap mint count per auction, cap global concurrent probes with
   backoff.
3. Avoid re-probing reachable mints every tick (cache TTL).

### Negative coverage
- A mint URL pointing at a private/loopback address is **not** contacted
  (assert `checkMintReachability` is never called with it / returns
  unreachable without a network call).
- Concurrency cap: N mints probed with a concurrency limit of K → at most
  K in flight.
