## 3. Exact completion and recipient-import authority

### 3.1 Authoritative records

The mint-side authority is the durable `DemoSigAllRecoveryRecord` and its exact
persisted terminal. The following equality is mandatory:

```text
completion.mintRequestDigest
  == recoveryRecord.requestDigest
  == terminal.requestDigest

completion.mintResponseDigest
  == terminal.responseDigest
```

The recipient-private journal must persist a V2 import-completion object only
after the wallet's idempotent import has succeeded. Its exact canonical order is:

```text
schema, operationId, role, recipientPublicKey, amount, proofCount,
recipientRequestDigest, recipientResponseDigest,
recipientImportIdempotencyKey, imported
```

The exact type is:

```ts
interface DemoRecipientImportCompletionV2 {
  readonly schema: "DemoRecipientImportCompletionV2";
  readonly operationId: string;
  readonly role: "winner_settlement" | "refund";
  readonly recipientPublicKey: string;
  readonly amount: number;
  readonly proofCount: number;
  readonly recipientRequestDigest: string;
  readonly recipientResponseDigest: string;
  readonly recipientImportIdempotencyKey: string;
  readonly imported: true;
}

interface DemoRecipientImportCompletionPortV2 {
  readExact(request: {
    readonly operationId: string;
    readonly role: "winner_settlement" | "refund";
    readonly recipientPublicKey: string;
    readonly amount: number;
    readonly recipientRequestDigest: string;
    readonly recipientResponseDigest: string;
    readonly recipientImportIdempotencyKey: string;
  }): Promise<DemoRecipientImportCompletionV2 | null>;
}
```

The port is a sanitized read of the authoritative private journal, not a new
authority. It returns no opening, unblinded proof, bearer token, or wallet
payload. The remaining mandatory equality is:

```text
completion.recipientRequestDigest
  == recipientJournal.requestDigest
  == importCompletion.recipientRequestDigest

completion.recipientResponseDigest
  == recipientJournal.importedResponseDigest
  == importCompletion.recipientResponseDigest

completion.recipientImportIdempotencyKey
  == importCompletion.recipientImportIdempotencyKey
  == SHA-256(UTF8("COCO_DEMO_RECIPIENT_IMPORT_V1\0" || recipientRequestDigest))
```

The R4 proof-count, amount, operation, recipient, bundle, template, selection,
and terminal-source equalities also remain mandatory. Missing journal values or
an extended receipt that cannot be traced to that journal fail closed.

`alreadyImported`, delivery route, and observation time stay outside immutable
completion. If the wallet imported before a crash but the journal was not yet
marked, restart calls the wallet with the same idempotency key, then atomically
persists the same V2 import-completion object. If the journal was marked before
the crash, `readExact` returns the same object. Therefore the R4 completion
canonical bytes and `completionDigest` are identical before and after restart.

### 3.2 Commit ordering

The required order is:

1. persist exact mint request identity before submission;
2. persist exact mint terminal metadata before recipient delivery;
3. idempotently import under the accepted import key;
4. atomically persist `DemoRecipientImportCompletionV2` in the recipient journal;
5. read and exact-match both durable journals; and
6. persist the immutable payment completion.

No completion may be inferred from a return value that was not durably recorded.

## 4. Ambiguous requests: no resubmission authority

R4.1 deletes `safe_to_retry` as an accepted execution transition. An opaque
`reconciliationId`, even if persisted or hashed, proves neither that the prior
request failed nor that it can no longer commit. For this delta:

```text
prepared and never attempted       -> one exact first submission may proceed
attempting/submitted_unknown        -> exact polling/recovery only
exact completed outcome recovered  -> persist terminal, restore response, import
bare SPENT                          -> manual_intervention_required
indeterminate/unknown               -> payment_pending
opaque safe_to_retry                -> manual_intervention_required
durable exact terminal              -> terminal restore/import only
```

`safe_to_retry` must not create `retry_ready`, increment an attempt, call the
mint, originate a new FROST session, or report success. Exact recovery may poll
for and verify the existing request's exact completed response. A bare proof
state or generic `SPENT` never selects MAIN/REFUND and never becomes completion.

The public result discriminant is extended without changing successful result
bytes:

```ts
type DemoPaymentNonterminalV2 =
  | { readonly status: "verification_pending"; readonly checkpointDigest: string; readonly phase: "history" | "approvals" }
  | { readonly status: "payment_pending"; readonly operationId: string; readonly reason: "submitted_unknown" | "indeterminate" }
  | { readonly status: "manual_intervention_required"; readonly operationId: string; readonly reason: "spent_only" | "unverified_retry_fence" };
```

A future retry transition requires an owner-accepted mint-side idempotency or
fence protocol whose exact bytes prove the earlier request cannot later commit.
No such capability exists in the accepted inputs, so R4.1 does not invent one.

## 5. Exact operation membership and approval snapshot

### 5.1 Membership

For expected `(authNetworkId, chainId, auctionId)` and closure height H, define
membership M by streaming verified canonical batches from height 1 through H:

1. Consider only bid entries whose batch domain and `auction_id` exact-match the
   expected scope and whose batch height is strictly less than H.
2. Every considered entry contributes exactly its tuple
   `(operation_id, bid_id, event_id, actor_id, amount, committed_height,
   committed_entry_index)`.
3. Operation id, bid id, event id, and the full tuple are each unique. A
   duplicate, conflicting replay, or alias rejects.
4. Displacement fields are all absent or all present. A present displaced tuple
   must exact-match one earlier M member, must have
   `displaced_refund_eligible == true`, and cannot refer forward or outside the
   expected scope. The replacement's own tuple is a distinct M member.
5. A member remains in M when displaced, refunded, settled, or already terminal.
   Terminal state suppresses duplicate effects; it does not remove the approval
   from replay commitments.
6. Rejected/uncommitted intents, unrelated auctions, and approvals without an M
   member are excluded. `no_bids` requires `|M| == 0`; `reserve_not_met` refunds
   all M members; `winner` assigns MAIN only to the exact closure winner and
   REFUND to every other M member.

The membership digest domain is
`COCO_DEMO_PAYMENT_OPERATION_MEMBERSHIP_V2\x00`. Its payload is the canonical
array of objects with exact field order `operationId, bidId, bidEventId,
bidderActorId, amount, committedHeight, committedEntryIndex`, populated from the
tuples above in immutable chain encounter order
`(committed_height, committed_entry_index)`. The verifier streams this order
while reading history, so it needs no unbounded sort. `operationMembershipSha256`
is recomputed from M; an input assertion is not authority.

The approval set contains exactly one verified ApprovalV2 for each M member and
no other approval. The approval must exact-match every member field plus the
expected scope. R4 duplicate rules still apply. The approval-set sort remains
`(authNetworkId, chainId, auctionId, operationId, approvalEventId)`.

Approval persistence exposes an immutable snapshot, never an unbounded list:

The page-digest domain is
`COCO_DEMO_PAYMENT_APPROVAL_SNAPSHOT_PAGE_V2\x00`. Its preimage is
`hexDecode(previousPageDigest) || uint64be(pageIndex) || canonicalPageBody`,
where the body is exactly `{schema,snapshotMarker,pageIndex,records,
cumulativeRecordCount,eof}` and excludes both roots/digests. The first previous
digest is 32 zero bytes. The snapshot-root domain is
`COCO_DEMO_PAYMENT_APPROVAL_SNAPSHOT_ROOT_V2\x00`; its descriptor order is:

```text
schema, snapshotMarker, authNetworkId, chainId, auctionId,
operationMembershipSha256, recordCount, pageCount, maxRecordsPerPage,
maxCanonicalApprovalBytesPerRecord, maxCanonicalApprovalArrayBytesPerPage,
finalPageDigest, verifiedApprovalSetSha256
```

Snapshot marker, snapshot root, prior/final/page digests, membership digest,
and approval-set digest are each exactly 64 lowercase hex characters.

Nonempty pages have 1..64 records strictly ordered by R4's approval-set tuple.
`eof` is true only on the
last page. `cumulativeRecordCount` is exact. For an empty set, `recordCount ==
pageCount == 0`, `finalPageDigest` is 32 zero bytes, and page 0 returns null.
For a nonempty set, `pageCount == ceil(recordCount/64)` and reading
`pageCount` returns null. A missing page, premature/late EOF, record after EOF,
count mismatch, reordered key, duplicate key, marker/root drift, or non-null
read after the committed EOF rejects. The payment verifier independently
recomputes membership, every approval, the page chain, and the approval-set
digest; snapshot metadata alone is not authority.

## 6. Deterministic history packing and resumable work

### 6.1 Packing and byte accounting

R4 history chunks are corrected as follows:

```text
packingPolicy = "greedy-contiguous-height-v1"
maxBatchesPerChunk = 64
maxCanonicalBatchUtf8Bytes = 65536
maxCanonicalBatchArrayUtf8BytesPerChunk = 4194304
```

For canonical batch byte strings `b[0..n-1]`, exact array payload bytes are:

```text
batchArrayUtf8Bytes = 2 + sum(UTF8Length(b[i])) + max(0, n - 1)
```

The two bytes are `[` and `]`; each separator is one comma byte. Packing starts
at height 1 and greedily appends the next height while `n <= 64`, each batch is
at most 65,536 bytes, and the resulting array payload is at most 4,194,304
bytes. If the next batch would exceed a bound, the current nonempty chunk closes
and the next chunk begins with that batch. A single oversized batch rejects;
it is never split, skipped, or truncated. Every chunk is nonempty and covers
exactly `lastHeight - firstHeight + 1` batches.

`DemoCommittedAuctionHistoryOpenV2` therefore adds, in this exact position
after `batchCount`:

```text
packingPolicy, maxBatchesPerChunk, maxCanonicalBatchUtf8Bytes,
maxCanonicalBatchArrayUtf8BytesPerChunk
```

The complete corrected open-object order is:

```text
schema, authNetworkId, chainId, firstHeight, throughHeight, throughAppHash,
immutableStorageMarker, storageRootSha256, chunkCount, batchCount,
packingPolicy, maxBatchesPerChunk, maxCanonicalBatchUtf8Bytes,
maxCanonicalBatchArrayUtf8BytesPerChunk, finalChunkDigest,
canonicalBatchHistorySha256
```

The root descriptor excludes `storageRootSha256` and otherwise uses this order:

```text
schema, authNetworkId, chainId, firstHeight, throughHeight, throughAppHash,
immutableStorageMarker, chunkCount, batchCount, packingPolicy,
maxBatchesPerChunk, maxCanonicalBatchUtf8Bytes,
maxCanonicalBatchArrayUtf8BytesPerChunk, finalChunkDigest,
canonicalBatchHistorySha256
```

Chunk index, first/last height, previous digest, and root/marker must agree. Reads are exactly
indices `0..chunkCount-1`; every committed index returns one chunk and index
`chunkCount` returns null. Any empty, missing, extra, duplicate, reordered,
gapped, overlapping, early-EOF, late-EOF, count, byte, or root conflict rejects.
The final counts must satisfy `batchCount == throughHeight` and the final height
and app hash must exact-match the open descriptor.

### 6.2 Authenticated resumable checkpoint

`processVerifiedBatches` does not scan unbounded history while holding one long
lock. Each invocation acquires the existing exclusive execution lock, reopens
and exact-matches immutable source roots, processes exactly one history chunk
or one approval page, atomically advances a checkpoint, performs no payment
effect, and returns `verification_pending`. Thus one verification invocation is
bounded to at most 64 batches/4,194,304 history bytes or 64 approvals/524,353
approval-array bytes. These are operational work bounds, not economic bid/fund
limits; every committed record remains required across resumptions.

Portable SHA-256 streaming state is persisted as:

```ts
interface DemoSha256StateV1 {
  readonly schema: "DemoSha256StateV1";
  readonly h: readonly [number, number, number, number, number, number, number, number];
  readonly totalBytes: number;
  readonly tailHex: string;
}
```

Each `h` word is uint32 after complete 64-byte compression blocks;
`totalBytes` is the safe-integer count of all bytes fed, and `tailHex` is the
lowercase encoding of exactly `totalBytes mod 64` uncompressed bytes (0..63).
History state begins after feeding `[`, then feeds canonical batches and commas,
and finalizes only after `]`. Approval state uses the same array framing. State
is validated by replaying the one bounded source page before accepting the next
checkpoint; malformed or inconsistent state rejects.

The checkpoint field order is:

```text
schema, revision, phase, authNetworkId, chainId, auctionId, closureHeight,
closureAppHash, immutableStorageMarker, storageRootSha256, nextChunkIndex,
nextHeight, verifiedBatchCount, previousChunkDigest, historySha256State,
operationMembershipSha256State, operationCount, operationMembershipSha256,
operationMembershipIndexMarker, operationMembershipIndexRootSha256,
approvalSnapshotMarker,
approvalSnapshotRootSha256, nextApprovalPageIndex, verifiedApprovalCount,
previousApprovalPageDigest, approvalSha256State, nextOperationIndex,
nextRecoveryIndex, terminalOperationCount, pendingOperationCount,
manualOperationCount, checkpointDigest
```

Its schema is `DemoPaymentVerificationCheckpointV2`; phase is
`history|approvals|ready|executing|payment_pending|consumed`. `checkpointDigest` uses
`COCO_DEMO_PAYMENT_VERIFICATION_CHECKPOINT_V2\x00` over all preceding fields.
The durable checkpoint store uses atomic compare-and-swap on revision and keeps
the derived operation-membership index under the same root/revision.
`operationMembershipSha256State` uses `DemoSha256StateV1` with canonical array
framing in encounter order. `operationMembershipSha256` and both approval
snapshot identifiers are null until history EOF freezes membership and opens
the exact snapshot; after that they are immutable. The membership index
marker/root bind the durable ordered member records built during the same
checkpoint CAS; both are exact lowercase 32-byte hex. The two operation indexes and
three counts are null until phase `ready` is atomically promoted to `executing`;
afterward they are safe integers atomically updated with the existing durable
per-operation record.

After the final page, a bounded final invocation closes both SHA streams,
checks history/snapshot counts and EOF, recomputes all expected commitments, and
persists phase `ready`. A later execution invocation reacquires the same lock,
reopens both immutable roots, exact-matches their markers/descriptors, verifies
the ready checkpoint and expected commitments, and atomically changes `ready`
to `executing` while claiming the closure and initializing the digest-bound
operation iterator. Source drift or a failed CAS produces zero
payment/FROST/mint/recipient effects. A crash before a
checkpoint commit reprocesses only that bounded unit; a crash after commit
resumes at its exact next index.

Execution is also bounded: each later invocation handles at most one exact
member operation or one exact recovery poll under that operation's durable
lock, then advances the checkpoint/status root. `winner` processes the exact
winner first and remaining members in encounter order; other nonempty outcomes
use encounter order. An already-terminal exact replay consumes one bounded
slot. Ambiguous/pending/manual state is durably recorded and does not become
success; remaining members may continue in later invocations. Phase becomes
`consumed` only when every member has exact terminal completion, or immediately
for verified `no_bids`. Otherwise it is `payment_pending`, and recovery visits
at most one nonterminal member per invocation. No operation is discarded
because a per-run ceiling was reached.

The corrected commitments object adds these exact fields after
`storageRootSha256`:

```text
operationMembershipSha256, operationCount, approvalCount
```

The full corrected commitment field order is:

```text
schema, authNetworkId, chainId, auctionId, closureHeight, closureAppHash,
immutableStorageMarker, storageRootSha256, operationMembershipSha256,
operationCount, approvalCount, canonicalBatchHistorySha256,
verifiedApprovalSetSha256
```

The snapshot marker/root remain payment-persistence checkpoint fields; they do
not cross the FIPS/UI interface and confer no new authority.

No auction-filtered snapshot, checkpoint, or local index becomes consensus
authority; it is a bounded verification aid tied to the independently
authenticated chain-wide root.

## 7. Authoritative cutoff clock and atomic session reservation

Caller-provided `nowSeconds()` is not cutoff authority. New MAIN authorization
uses one durable store transaction:

```ts
interface DemoMainSessionReservationV2 {
  readonly schema: "DemoMainSessionReservationV2";
  readonly clockPolicyVersion: "durable-monotonic-executor-seconds-v1";
  readonly clockId: string;
  readonly observedSeconds: number;
  readonly attemptNumber: number;
  readonly sessionId: string;
}

reserveMainSessionBeforeCutoff(request: {
  readonly scope: string;
  readonly bundleDigest: string;
  readonly selectionRoot: string;
  readonly cutoffSeconds: number;
  readonly expectedClockId: string;
  readonly clockPolicyVersion: "durable-monotonic-executor-seconds-v1";
}): Promise<DemoMainSessionReservationV2>;
```

Inside the same atomic transaction, the store samples its configured executor
clock, exact-matches the pinned `clockId` and policy, loads the durable last
observation, rejects `observedSeconds < lastObservedSeconds`, rejects
`observedSeconds >= cutoffSeconds`, updates the monotonic floor, reserves the
next never-used attempt number, derives the exact session id, and commits both.
No FROST message may be emitted before that commit. Clock rollback, clock-id
change, missing durable floor after a prior reservation, unavailable clock, or
restart state conflict refuses; it does not fall back to process time.

The same pinned clock/floor gates local REFUND eligibility at `observedSeconds
>= locktime`. This is only a consistent local scheduling policy. It does not
prove mint time, alter NUT-11 enforcement, revoke a previously completed MAIN
signature, or remove the post-locktime first-spend race. A trusted external or
mint-attested time service would change the trust/product model and needs a new
owner decision; R4.1 claims no stronger guarantee.

## 8. Signed grammar and byte ceilings

Every ApprovalV2 value first passes exact field grammar, then canonical byte
limits, before signing or verification:

| Field(s) | Exact grammar/limit |
|---|---|
| `chainId`, `auctionId`, `operationId`, `bidId` | `^[\x21-\x7e]{1,160}$` |
| `authNetworkId`, `bidEventId`, `bidderActorId`, every digest/fingerprint/event id | exactly 64 lowercase hex characters |
| B/C/seller/committee compressed public keys | `^(02|03)[0-9a-f]{64}$` |
| BIP340 signatures | exactly 128 lowercase hex characters |
| schema and policy versions | exact literals frozen by R4; no aliases |
| `sellerP2pkXpub` | printable ASCII 1..160 plus valid Base58Check xpub/tpub; xprv/tprv and unknown versions reject |
| `sellerDerivationPath` | canonical `m/a/b/c/d/e`; five decimal levels, no leading zero except `0`, each `0..2147483647`, printable ASCII and at most 160 bytes |
| `mintUrl` | printable ASCII 1..160 and byte-equal to `new URL(value).origin`; HTTPS; no credentials, explicit port, path, query, fragment, trailing slash, Unicode/noncanonical host spelling, or normalization drift |
| timestamps/counts/amounts | safe integers with the positive/nonnegative rule already frozen for each field |

The exact kind-28643 content UTF-8 length is at most 4,096 bytes. The complete
canonical ApprovalV2 UTF-8 length is at most 8,192 bytes. Each snapshot record
must satisfy that 8,192-byte limit. For a page of n records, exact canonical
array bytes are `2 + sum(recordBytes) + max(0,n-1)` and must not exceed 524,353.
All limits count canonical UTF-8 bytes, not UTF-16 code units. Rejection occurs
before signing, snapshot admission, digesting, or any downstream call.

## 10. Targeted acceptance tests

1. **Completion:** each of the four digest mismatches refuses; unpersisted
   return values refuse; crashes before/after wallet import and before/after
   journal mark reproduce byte-identical completion and digest; diagnostics may
   change without changing completion.
2. **Retry:** `safe_to_retry`, bare `SPENT`, and opaque reconciliation ids make
   zero mint/FROST calls; exact completed polling restores; indeterminate stays
   pending; manual and success results cannot be confused.
3. **Membership:** unrelated auction approvals excluded; missing/extra member,
   displacement forward/mismatch, replacement, terminal replay, duplicate tuple,
   count/page/EOF/root drift, empty no-bid set, and every outcome mapping.
4. **History/work:** exact 64/65 chunk boundaries, 65,536-byte batch boundary,
   4,194,304-byte array boundary, greedy packing, oversized singleton, empty or
   extra chunk, gap/overlap, early/late EOF, crash before/after checkpoint CAS,
   one-chunk/page and one-operation/poll ceilings, multi-call verification and
   execution, pending/manual operation continuation, and final root drift with
   zero effects.
5. **Clock:** just-before/equal/after cutoff, atomic reserve failure, two-process
   race, restart, backward clock, changed clock id, missing floor, unavailable
   clock, retained completed MAIN after cutoff, REFUND before/at locktime, and
   explicit first-spend-race preservation.
6. **Grammar:** every signed text at 0/1/160/161 bytes; space, control, DEL,
   non-ASCII, surrogate/U+FFFD, malformed xpub, private key version, path depth,
   hardened/leading-zero/out-of-range path, URL case/port/path/query/fragment/
   slash/credential normalization, 4,096/4,097 content bytes, 8,192/8,193
   approval bytes, and exact page-byte boundary.

Allowed evidence remains targeted offline Bun tests, strict TypeScript, sealed
binary hashes, and `cargo test --offline --locked` only for a separately
authorized Rust change. No network, dependencies, runtime/service/listener,
external mint, DKG, real key/share/fund, credential, commit, push, deployment,
or publication action is authorized.

## 11. Remaining owner/trust decisions

Only two requested semantics cannot be strengthened within the current trust
model:

1. **Ambiguous resubmission:** enabling it requires an exact accepted mint-side
   idempotency/fence capability. Until owner and mint authority freeze that
   protocol, ambiguous operations remain pending/manual and are never retried.
2. **Stronger cutoff time:** the frozen monotonic executor clock prevents local
   rollback/restart mistakes but does not prove mint time. Any externally trusted
   or mint-attested clock is a product/trust-model change requiring owner choice.

Storage adapter/snapshot acceptance and integration order remain coordination
checkpoints, not new product authority. Missing acceptance refuses before all
payment effects. No source behavior or test result is claimed by this document.
