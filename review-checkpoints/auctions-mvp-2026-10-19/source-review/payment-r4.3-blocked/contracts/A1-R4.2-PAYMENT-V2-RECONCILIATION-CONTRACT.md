## 2. Exact `committedEntryIndex` semantics

For each already authenticated canonical `CommittedAuctionBatchV2` at height
`h`, the verifier enumerates the exact original `bids` array as
`batch.bids.entries()` before applying any auction, disposition, terminal,
operation, displacement, or other filter.

For an entry at array position `i`:

```text
committedHeight     = h
committedEntryIndex = i
```

`committedEntryIndex` is therefore the zero-based position in the original
canonical `CommittedAuctionBatchV2.bids` array. Filtering may exclude an entry
from membership M but never renumbers a retained entry. The index is a
nonnegative safe integer and is strictly less than the original array length.
The chain encounter order remains `(committedHeight, committedEntryIndex)`.

## 3. Exact ApprovalV2 join and membership-only provenance

For each M member, there must be exactly one otherwise-valid verified
ApprovalV2. The approval joins to that member using exactly these fields:

```text
approval.authNetworkId == expected.authNetworkId
approval.chainId        == expected.chainId
approval.auctionId      == expected.auctionId
approval.operationId    == member.operationId
approval.bidId          == member.bidId
approval.bidEventId     == member.bidEventId
approval.bidderActorId  == member.bidderActorId
approval.amount          == member.amount
```

Those are the expected scope plus `operationId`, `bidId`, `bidEventId`,
`bidderActorId`, and `amount`. No ApprovalV2 field exists or is added for
`committedHeight` or `committedEntryIndex`. Those two values are
membership-only provenance authenticated by the independently recomputed
`operationMembershipSha256`. The ApprovalV2 field order, canonical bytes,
signature, digest, and approval-set ordering remain unchanged.

## 4. Durable legacy `retry_ready` compatibility

A record written by pre-R4.1 code with
`schema == "COCO_DEMO_SIGALL_RECOVERY_V1"` and `state == "retry_ready"` is
preserved as historical durable evidence. Its `reconciliationDigest`, whether
present, absent, valid, malformed, known, or unknown, grants no retry authority.

On compatibility read:

1. validate and bind the record to the exact stored scope, operation root,
   request digest, proof-state refs, outputs, capability, seal, and role under
   the existing rules;
2. do not clear, rewrite, delete, upgrade in place, renumber, or otherwise
   destructively migrate the stored record or its reconciliation digest;
3. do not create a FROST session, increment an attempt, derive a new request,
   or call mint submission;
4. absent an exact already-established completed outcome, return
   `manual_intervention_required` with reason `unverified_retry_fence`; and
5. exact read-only recovery may still poll for one already-established completed
   outcome under R4.1's one-poll work bound. If and only if the returned response
   exact-matches the stored request and all accepted terminal checks, persist the
   exact terminal, restore/import it, and complete under R4.1. This is recovery
   of an existing outcome, never resubmission.

A repeated `safe_to_retry`/opaque result during such polling still produces
`manual_intervention_required/unverified_retry_fence`, preserves the legacy
record, and makes zero new FROST or mint-submission calls. A legacy record that
already has an exact valid terminal is handled by the established terminal
restore/import path and is not downgraded merely because older evidence also
contains a reconciliation digest.
